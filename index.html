V0 · 起点
02

最开始，我和 AI 就是一问一答

没有流程，没有角色，没有验证。每次对话都从头说清楚背景，AI 做完给我看，我说不对，它改，如此循环。

典型对话模式
我
帮我把这个思维导图的节点拖拽做出来，参考这份设计稿……（粘贴了 800 字描述）
AI
好的，我来实现拖拽功能，这里我用了 react-draggable……（生成了 200 行代码）
我
不对，不是 react-draggable，我们用的是 XYFlow，你没记住之前说的。
AI
抱歉，让我重新做……（新会话开始，又忘了之前的所有约定）
核心问题
  • 每次对话要重新交代背景，成本极高
  • AI 没有记忆，规则约定全靠 prompt 传递
  • 没有验证环节，"做完"不等于"做对"
  • Context 越来越长，输出质量越来越差
本质缺失

没有流程承载规则， 没有角色划分职责， 没有验证保证质量。 这不是 AI 的能力问题，是协作方式的问题。

我需要的不是"更好地和 AI 聊天"，而是"搭一套让 AI 能稳定工作的体系"。

03

把规划和执行拆开——这是最重要的一步

参考了优秀的 agent 配置实践后，核心判断是：一问一答不是 AI 的极限，而是协作架构的极限。把"想明白"和"做出来"拆开，才能真正发挥 AI 的潜力。

单模型多 Agent 架构
用户
↓
Codewiz 主 Agent
规划 · 编排 · Review · 决策
↙                 ↘
子 Agent 1
独立上下文·执行 Task-1

独立上下文·执行 Task-2
收益 1 — 上下文精简

主线程只留决策

研究、探索和并行分析交给子 Agent。主上下文窗口保持干净，输出质量稳定。

收益 2 — 天然带 Review

规划与执行相互校正

拆开之后，主 Agent 对子 Agent 的结果天然存在一道 Review 关卡。

收益 3 — 成本可控

高频执行用轻量 Agent

高价值规划用更稳的模型，高频执行用成本更低的模型，整体成本可控。

"从'我和 AI 聊一聊'，变成'我带着一个 AI 团队做项目'。"

V2 · 关键转折 — 工作习惯
04

参考优秀的 Agent 配置后，我意识到：
真正让项目不跑偏的不是 Prompt，而是工作习惯

规则要写进文件，不能靠对话传递。于是有了 AGENTS.md——一个每次会话启动时 AI 必须读取的"团队宪法"。

Plan 优先

复杂任务先写 Spec

超过 3 步或涉及架构判断，先写范围、验收和风险，再动手。

## spec
- 目标：完成导出链路
- 范围：仅 PDF / PNG
- 验收：能导出且不丢节点
- 风险：大图性能、分页裁切
子 Agent 拆出去

研究和并行分析独立

主上下文只保留当前决策，避免一个窗口里塞满所有细节。

agent A：研究导出方案
agent B：排查状态持久化
agent C：对比主流 mindmap 库

主线程只保留结论与决策
Lessons 沉淀

每次纠正写进文件

把反复出现的错误变成默认规则，不靠每次重新提醒。

## lessons
- 设计稿不能直接进开发
- 先转 PRD 再 handoff
- 任务完成前必须留验证证据
Task Management

任务清单持续勾选

计划、进度、review 都落在同一个文件，做完一项勾一项。

- [x] 明确导出范围
- [x] 拆分实现步骤
- [ ] 跑回归测试
- [ ] 补 review 小结
AGENTS.md 核心条款 
## 任务分级与强制流程

🟢 小任务（≤2步，单文件）
→ 直接实现 → verify → 完成

🟡 中任务（3-6步，跨2个模块）
→ 写 plan → 实现 → 两阶段 review → 完成

🔴 大任务（跨模块/架构调整）
→ brainstorming → 写 spec → 实现
→ 两阶段 review → 完成

## 两阶段 Review 门控

阶段 1：Spec 合规 Review
- spec 中每条需求是否都有对应实现？
- 边界条件和错误处理是否覆盖？

阶段 2：代码质量 Review
- 类型安全？相同逻辑是否超过 2 处？
- 是否有明显的回归风险？

两关都通过才算完成。

## 完成定义（DoD）
- [ ] 功能可运行
- [ ] npm run build 通过
- [ ] 两阶段 review 通过
- [ ] 无明显回归风险

治理体系 · prd-registry + DoR/DoD
06

光靠工作习惯还不够，需要一套治理框架来管项目生命周期

多个 PRD 同时进行时，每次会话"从哪里接着做"变成了问题。于是引入 prd-registry.md 作为唯一主控文件。

prd-registry.md

PRD 驱动开发

  • Active PRD 唯一可见
  • 会话启动：先读 registry，告知用户下一步
  • 任务完成自动更新状态
  • 队列管理：完成一个取下一个
会话启动协议：
"当前 Active PRD 是 [导出链路]，
下一步是 [实现 PDF 导出]，
确认继续？"
DoR — 需求准入

进开发前必须通过

  • 需求背景和目标清晰？
  • 验收标准（AC）已定义？
  • 设计稿已就绪或明确不需要？
  • 依赖项已解决？
  • 范围边界已确认？
不满足 DoR → 禁止进入开发
DoD — 完成定义

全部满足才算完成

  • 功能可运行
  • npm run build 通过
  • 两阶段 Review 通过
  • 无明显回归风险
  • 关键变更有注释
不满足 DoD → 视为未完成
治理的价值不是限制，而是让 AI 和人都知道"做到什么程度算完成"。

架构守护 · 改 5 处 → 改 1 处
07

加了 LR/TB 两种布局，布局 Bug 悄悄出现了

导出 PNG 时连接线方向全部错误。深查发现：同一套"方向"逻辑散落在 5 个文件里互不知晓——这是"先快速跑起来"积累的典型技术债。

✗ Before — 布局规则散落 5 处
// EditorPage.tsx if (isLR) sourceHandle = 'source-right' else sourceHandle = 'source-bottom' // MindmapNode.tsx if (mode==='left-right') position=Right else position=Bottom // snapshot.ts sourcePosition: Position.Right ← 硬编码! targetPosition: Position.Left // + FoldButton.css / AddButton.css ...
新增布局 RL → 需要改 5 个文件，极易漏改
✓ After — 单一数据源 layoutConfig.ts
// layout/layoutConfig.ts ← 唯一改动处 'right-left': { sourceHandleId: 'source-left', sourcePosition: Position.Left, exportSourcePosition: Position.Left, foldButton: { side: 'left', ... }, } // EditorPage / MindmapNode / snapshot.ts const cfg = getLayoutConfig(mode) // 自动适配
新增布局 RL → 只改 1 个文件，其余自动适配
沉淀进 AGENTS.md §9 — 架构守护
  • 1相同逻辑出现 2+ 处 → 必须抽取
  • 2新功能引入新"维度" → 必须建配置入口
  • 3发现架构问题 → 禁止沉默，必须向用户说明技术债和收益

Takeaways · 实践洞察
10

五条真实踩出来的经验

Lesson 1

先跑通最小闭环

0-1 最重要的不是做得全，而是先验证"能不能跑通"，再决定往深处做。

Lesson 2

习惯 > Prompt

真正让项目稳定的是写进文件的工作方式，不是一句神奇的提示词。

Lesson 3

规则要写成文件

每次被纠正的错误，都要沉淀成 AGENTS.md 里的规则，而不是在 prompt 里重复。

Lesson 4

早期架构值得投入

早期多花 2 小时做架构设计，等于省去后期 20 小时的技术债偿还。

Lesson 5

把方法做成可复用 Skill

分享不是终点。最后留下来的，是一套别人也能直接启动的项目模板。
