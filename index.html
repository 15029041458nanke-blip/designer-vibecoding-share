② 工作习惯 · 参考优秀配置指南
03

参考优秀但片段式的开发 Agent 配置指南后，
我意识到：真正让项目不跑偏的不是 Prompt，而是工作习惯

规则必须写进文件，不能靠对话传递。每次被纠正的错误要沉淀为规则，不靠每次重新提醒。于是有了 AGENTS.md。

Plan 优先

复杂任务先写 Spec

超过 3 步或涉及架构判断，先写范围、验收和风险，再动手。

## spec
- 目标：完成导出链路
- 范围：仅 PDF / PNG
- 验收：能导出且不丢节点
- 风险：大图性能、分页裁切
子 Agent 拆出去

主线程只留决策

研究和并行分析交给子 Agent，主上下文只保留当前决策。

agent A：研究导出方案
agent B：排查状态持久化
agent C：对比主流 mindmap 库
主线程只保留结论与决策
Lessons 沉淀

错误变成规则

每次被纠正后写进文件，让它成为下次会话的默认行为。

## lessons
- 设计稿不能直接进开发
- 先转 PRD 再 handoff
- 完成前必须留验证证据
两阶段 Review

做完 ≠ 做对

Spec 合规 + 代码质量两关都过，才算完成任务。

阶段1：spec需求全实现了吗？
        边界条件覆盖了吗？
阶段2：类型安全？相同逻辑>2处？
        有回归风险吗？
AGENTS.md · 任务分级强制流程 
🟢 小任务（≤2步，单文件）
直接实现 → verify → 完成

🟡 中任务（3-6步，跨2模块）
写 plan → 子 Agent 实现
→ 两阶段 review → 完成

🔴 大任务（跨模块/架构调整）
brainstorming → 写 spec
→ 子 Agent 实现（每 task 独立）
→ 两阶段 review → 完成

不允许跳级：大任务不得直接
进入实现，必须完成规划串联。

── 完成定义（DoD）──
☑ 功能可运行
☑ npm run build 通过
☑ 两阶段 Review 通过
☑ 无明显回归风险
☑ 关键变更有注释

两关都通过才算完成。
不满足 DoD 一律视为未完成。

③ 设计角色 · design-analyst 的引入与迭代
04

接入 Figma MCP，补上了设计角色——
这是让开发质量真正上台阶的一步

设计稿不能直接进开发：颜色没有 token 映射，组件边界不清，hover 状态靠猜。有了 design-analyst，设计意图变成工程可接手的 PRD。

引入背景 · 为什么需要这个角色
  • 手写 PRD 遗漏设计细节，工程执行靠猜
  • 颜色值散落、间距规则不统一，每次都要反复确认
  • 接入 Figma MCP 后，AI 能直接读设计稿数据
  • design-analyst 上线，负责把设计翻译成工程格式
优化迭代过程 · 每踩一个坑，规范就多一条
① 首版只输出组件名 → 补充 token 映射要求
② 缺 hover/disabled 状态 → 强制输出全状态定义
③ 边界不清楚 → 加入验收标准（像素级还原约束）
④ 响应式没定义 → 补充断点行为规范
⑤ Figma 特殊属性漏读 → 沉淀成 7 章节规则库
最终产出 · design-role-rules.md

411 行实战沉淀的 Figma→CSS 还原规则库

字体 & 行高
间距规则
颜色 Token
全状态定义
响应式断点
Figma 特殊属性
组件 → 代码映射

每次踩坑都更新，越用越精准

没有 design-analyst · 手写 PRD
需求：
- 页面风格和 Figma 保持一致
- 顶部有搜索和操作区
- 卡片要有 hover 状态
- 颜色和间距尽量还原

问题：哪些是组件不清楚；
颜色没有 token 映射；
工程拿到后仍然要猜
加入 design-analyst · 自动解析
组件映射：
- SearchInput → Input/Search
- ViewSwitch → SegmentedControl
- PrimaryAction → Button/Primary

设计约束：gap-16 / padding-x-24
状态定义：default/hover/active/disabled
验收标准：
  所有颜色必须走 design tokens
  Header 高度 72px 不允许漂移
  卡片 hover：shadow-md + bg-hover
这不只是工具升级，而是从"描述设计"到"定义实现"的质变。

④ 治理体系 · prd-registry + DoR/DoD
05

光靠工作习惯还不够——需要一套治理框架
来管多个 PRD 并行时"从哪里接着做"的问题

多个 PRD 同时进行时，每次会话"从哪里接着做"变成了问题。于是引入 prd-registry.md 作为唯一主控文件，配合 DoR/DoD 构成完整治理闭环。

prd-registry.md

PRD 驱动开发

  • Active PRD 唯一可见
  • 会话启动：先读 registry，告知用户下一步
  • 任务完成自动更新状态
  • 队列管理：完成一个取下一个
会话启动协议：
"当前 Active PRD 是 [导出链路]，
下一步是 [实现 PDF 导出]，
确认继续？"
DoR — 需求准入

进开发前必须通过

  • 需求背景和目标清晰？
  • 验收标准（AC）已定义？
  • 设计稿已就绪或明确不需要？
  • 依赖项已解决？
  • 范围边界已确认？
不满足 DoR → 禁止进入开发
DoD — 完成定义

全部满足才算完成

  • 功能可运行
  • npm run build 通过
  • 两阶段 Review 通过
  • 无明显回归风险
  • 关键变更有注释
不满足 DoD → 视为未完成
治理的价值不是限制，而是让 AI 和人都知道"做到什么程度算完成"。

⑤ 架构守护 · 改 5 处 → 改 1 处
06

加了 LR/TB 两种布局，布局 Bug 悄悄出现了

导出 PNG 时连接线方向全部错误。深查发现：同一套"方向"逻辑散落在 5 个文件里互不知晓——这是"先快速跑起来"积累的典型技术债。

✗ Before — 布局规则散落 5 处
// EditorPage.tsx if (isLR) sourceHandle = 'source-right' else sourceHandle = 'source-bottom' // MindmapNode.tsx if (mode==='left-right') position=Right else position=Bottom // snapshot.ts sourcePosition: Position.Right ← 硬编码! targetPosition: Position.Left // + FoldButton.css / AddButton.css ...
新增布局 RL → 需要改 5 个文件，极易漏改
✓ After — 单一数据源 layoutConfig.ts
// layout/layoutConfig.ts ← 唯一改动处 'right-left': { sourceHandleId: 'source-left', sourcePosition: Position.Left, exportSourcePosition: Position.Left, foldButton: { side: 'left', ... }, } // EditorPage / MindmapNode / snapshot.ts const cfg = getLayoutConfig(mode) // 自动适配
新增布局 RL → 只改 1 个文件，其余自动适配
沉淀进 AGENTS.md §9 — 架构守护
  • 1相同逻辑出现 2+ 处 → 必须抽取
  • 2新功能引入新"维度" → 必须建配置入口
  • 3发现架构问题 → 禁止沉默，必须向用户说明技术债和收益

⑥ Superpowers Skill · 子 Agent → 子 SKILL 的进化
07

引入 GitHub 高星开发全家桶 Skill 后，
随机子 Agent 变成了结构化的子 SKILL

Superpowers 是社区沉淀的最佳实践 Skill 集，引入后结合我们自己的 design-analyst 角色，最终构成了完整协作形态。最关键的进化是：从"随机调用子 Agent"到"有规范的子 SKILL"。

以前 · 随机子 Agent（临时指派）
每次临时说"你现在扮演 Reviewer"
提示词散落在对话里，无法复用
没有触发条件，靠记忆决定何时调用
输出格式不固定，每次结果不一样
新会话全部忘记，重新口头约定
现在 · 结构化子 SKILL（规范触发）
skills/two-stage-review/SKILL.md
  触发条件：每个 task 完成后
  Phase-1：Spec 合规 Review
  Phase-2：代码质量 Review
  输出：通过/不通过 + 修复清单

skills/design-analysis/SKILL.md
  触发条件：有 Figma 链接输入时
  Phase-1：设计分析包
  Phase-2：Design QA（苛刻还原验收）
7 个结构化子 SKILL（Superpowers + 自定义）
design-analysis Figma 读稿 → 设计分析包 → Design QA
requirements DoR 检查 + AC 补全 → 完整 PRD
sys-debugging 四阶段 Debug，根因必须先找到
writing-plans No Placeholder 规定，每步必须有验证
brainstorming 需求不清时的探索规范
two-stage-review Spec 合规 + 代码质量两关门控
arch-check 架构变更前强制扫描，禁止沉默
最终协作形态 = Superpowers Skill + 自定义设计角色
design-analysis + requirements + writing-plans + two-stage-review + arch-check

每个 SKILL 都有：触发条件 · 执行步骤 · 输出产物 · 禁止清单。不靠记忆，一触即发，输出稳定。

核心判断
习惯 > Prompt  ·  SKILL > Agent  ·  规则写文件 > 对话口述
子 SKILL 是最稳定、最可复用的协作单元。

10

五条真实踩出来的经验

Lesson 1

先跑通最小闭环

0-1 最重要的不是做得全，而是先验证"能不能跑通"，再决定往深处做。

Lesson 2

习惯 > Prompt

真正让项目稳定的是写进文件的工作方式，不是一句神奇的提示词。

Lesson 3

规则要写成文件

每次被纠正的错误，都要沉淀成 AGENTS.md 里的规则，而不是在 prompt 里重复。

Lesson 4

早期架构值得投入

早期多花 2 小时做架构设计，等于省去后期 20 小时的技术债偿还。

Lesson 5

SKILL > Agent · 结构化优于临时指派

随机子 Agent 靠记忆触发，每次结果不同。结构化子 SKILL 有触发条件、步骤、产物，输出稳定可复用。
